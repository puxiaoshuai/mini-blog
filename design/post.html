TypeScript: interface vs type 终极指南

面向全栈工程实践（Node.js + React），提供可落地的选择标准与团队约定。

蒲

蒲小帅 博主

2026.08.07 · 8 分钟阅读

17 次浏览

在 TypeScript 社区里，interface 与 type 之争几乎每周都会被翻出来一次。 两个看起来都能定义结构的关键字，用起来却各有脾气。这篇指南不做学术辩论，只给结论—— 面向全栈工程实践（Node.js + React），提供可以直接落地的选择标准。

01 一句话速记

✅ 对象结构 / API 契约 → interface

✅ 组合、变换、联合、工具类型 → type

更口语化一点：

  • 「这是个东西」→ interface
  • 「这是种关系 / 变形」→ type

02 决策表（速查）

场景 推荐 原因
对象 / DTO / VO / Propsinterface语义清晰、可扩展
API 请求 / 响应结构interface贴近契约、易维护
联合类型 / 交叉类型typeinterface 不支持
字面量联合（替代 enum）type唯一选择
可辨识联合 Discriminated Uniontype事实标准
扩展第三方类型（声明合并）interfacetype 做不到
工具类型 / 条件 / 映射类型typeinterface 做不到

03 本质差异

interface 面向「对象结构」——语义是「实现这个契约」，设计目标是 OOP、继承、扩展；支持声明合并与 extends 继承，更适合人类阅读。

src/types/user.ts复制interface User {
  id: number;
  name: string;
}

读起来像：「User 是一个拥有 id 和 name 的对象」。

type 则面向「类型关系」——语义是「这是某种类型」，设计目标是类型别名、组合与变换：联合 |、交叉 &、条件类型 T extends U ? A : B、映射类型。

type ID = number | string;
type UserOrError = User | Error;

读起来像：「ID 可以是 number 或 string」。

04 常见误区

误区一：用可选属性模拟联合。下面这样写，TS 无法强制「email / phone 至少存在一个」，运行时还得自己校验：

// ❌ 不推荐
interface User {
  id: number;
  email?: string;
  phone?: string;
}

✅ 正确做法是交给可辨识联合：

type Contact =
  | { kind: 'email'; email: string }
  | { kind: 'phone'; phone: string };

误区二：同一层级风格混用。一个 interface、一个 type、再来个交叉拼接，团队里谁也记不住规则。原则是：同一「层级」的类型，尽量统一 interface 或 type。

05 生产团队约定（可直接抄）

前端 / React：Props / State / Ref 用 interface；事件回调、状态集合用 type。Node / API：请求响应用 interface；业务结果、工具类型用 type。

src/types/api.ts复制interface CreateUserReq { email: string; password: string; }
interface CreateUserRes { id: number; email: string; }

type ServiceResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string };

type Maybe<T> = T | null | undefined;

interface = 定义「是什么」；type = 描述「是什么关系」。定义对象形状 → interface，组合 / 变换 / 联合 → type。同一项目内保持风格一致，比选哪个更重要。

—— 一句话终极总结 · 文档版本 1.0 | TypeScript 5.x | 2026-08-07

附录里还有一条联合类型速览：赋值时符合任意一个即可，使用时只能访问所有类型共有的成员，必须通过类型收窄才能安全使用特定成员。
